## 문제와 제약

사용자는 대회를 탐색하고 신청 상태를 확인해야 하지만, 운영자 시스템은 좌석 배정과 실제 현장 업무를 책임집니다. 회원 정보 역시 별도 시스템이 소유할 수 있습니다. 사용자용 서비스를 만드는 과정에서 **화면에 필요한 정보와 서비스가 실제로 소유한 권한**을 구분해야 했습니다.

## 맡은 범위

React 사용자·관리자 화면, Express API, PostgreSQL·Prisma 기반 저장소를 구성했습니다. 대회·공지의 공개 조회, 신청·취소 요청과 관리자 처리, 로컬 세션과 프로필 경계를 다뤘습니다.

## 핵심 판단

### 직접 연결보다 계약을 먼저 분리했습니다

외부 회원·운영 시스템은 Adapter를 통해 연결하도록 경계를 두었습니다. 사용자 웹이 외부 운영 데이터베이스나 런타임을 직접 변경하지 않도록 역할을 제한했습니다.

### 공개 데이터와 내부 데이터를 나눴습니다

공개 상태의 대회만 조회하고, 화면에 필요한 사용자용 데이터 구조를 따로 매핑했습니다. 내부 식별자와 외부 시스템의 정보가 그대로 사용자 응답으로 새지 않도록 설계했습니다.

### 자체 기능의 완료와 실연동 완료를 구분했습니다

자체 세션을 이용한 사용자·관리자 흐름은 독립적으로 검증하되, 그것을 외부 로그인이나 실제 운영 시스템 연동의 성공 증거로 사용하지 않았습니다. 미확정 계약이나 외부 환경이 필요한 작업은 별도 검증 단계로 남겼습니다.

## 반복 구조와 도메인 경계

요청 식별자, 오류 응답, 검증, 인증 문맥은 공통 API 기반으로 구성했습니다. 반면 회원 정보의 소유권, 대회 운영 권한, 사용자 신청의 상태 전이는 서로 다른 경계로 유지했습니다.

## 검증 방식

단위 테스트, PostgreSQL 연동 테스트, 브라우저 테스트를 구분했습니다. API 응답을 대체하는 UI 테스트와 실제 Express·PostgreSQL을 사용하는 E2E도 나누어, 각 테스트가 증명하는 범위를 명확하게 했습니다.

## 결과와 공개 범위

자체 사용자 기능과 관리자 기능의 구현 기반, 외부 서비스와 연결할 수 있는 Adapter·API 계약 경계를 마련했습니다. 프로젝트 자료상 일부 외부 동기화와 실제 공급자 검증은 별도 단계이므로, 전체 실연동이 완료된 서비스로 표현하지 않습니다.

이 프로젝트의 핵심은 단순한 CRUD가 아니라 **내가 소유한 기능과 외부 시스템의 권한을 구분하면서 제품을 구성한 경험**입니다.
