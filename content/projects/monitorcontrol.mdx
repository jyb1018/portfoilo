## 문제와 제약

여러 매장의 디스플레이에 광고 콘텐츠와 포커 클락을 표시해야 했습니다. 대상은 브라우저만이 아니라 실제 Android TV 기기였으며, 네트워크 상태·콘텐츠 저장·앱 업데이트 같은 현장 조건까지 고려해야 했습니다.

## 맡은 범위

React 관리자 웹, Express·TypeScript 서버, PostgreSQL 저장소와 Kotlin Android TV 앱을 연결했습니다. 기기 등록과 승인, 콘텐츠 정책, 실시간 명령, 상태 보고, 콘텐츠·APK 배포에 필요한 기반을 구성했습니다.

## 실제 운영 규모

**4개 매장에서 사용되었으며, 그중 한 매장에 38대 기기가 있습니다.** 이 수치는 현장 사용 규모이며, 전체 매장의 합산 기기 수나 동시 부하 테스트 결과를 뜻하지 않습니다. 운영 위치와 기기 식별정보는 공개하지 않습니다.

## 핵심 판단

### 콘텐츠와 제어 경로를 나눴습니다

관리자 웹과 서버는 정책과 명령을 다루고, Android 앱은 콘텐츠 재생과 기기 상태를 책임지도록 구성했습니다. 실시간 명령은 WebSocket으로 전달하고 heartbeat를 통해 장치 상태를 확인하는 구조를 사용했습니다.

### 네트워크 단절이 재생 중단으로 이어지지 않게 했습니다

기기는 검증된 콘텐츠를 로컬에 보관하고 마지막 유효 콘텐츠를 활용하도록 설계했습니다. 저장된 manifest를 검증하고 복구 가능한 후보를 읽는 방식으로 잘못된 데이터와 정상 콘텐츠를 구분했습니다.

### 보낸 정책과 적용된 상태를 구분했습니다

서버가 원하는 정책을 저장했다고 기기에 이미 적용된 것은 아닙니다. 목표 정책과 heartbeat로 보고된 실제 재생·캐시·오류 상태를 나누어 관리자가 적용 여부를 확인할 수 있도록 구성했습니다.

## 공통화와 현장별 설정

기기 등록, 인증, 상태 보고, 정책 전달, 업데이트 경로는 공통화했습니다. 반면 콘텐츠, 표시 URL, 적용 범위와 재생 방식은 설정으로 구분했습니다. 매장별로 별도 앱을 만드는 대신 하나의 제어 기반에서 차이를 표현하는 방향입니다.

## 새로운 기술을 적용한 과정

웹 밖의 실행 환경을 다루기 위해 Kotlin Android 앱, 로컬 콘텐츠 저장과 기기 제어 경로까지 범위를 확장했습니다. 서버·관리자 웹·Android를 나눠 검증하고, 에뮬레이터와 물리 기기 확인 절차를 별도로 두는 방식으로 접근했습니다.

## 결과와 다음 지표

실제 여러 매장에서 사용하는 중앙 제어 기반을 제공했습니다. 현재 공개하는 정량 성과는 매장 수와 단일 매장 기기 수입니다. 장애 감소율이나 작업시간 절감률은 측정하지 않은 수치를 만들어 넣지 않았습니다.

추가 계측 시에는 콘텐츠 적용 성공률, 목표 정책과 기기 보고 사이의 지연, 오프라인 복구 시간 등을 운영 지표로 삼을 수 있습니다.
