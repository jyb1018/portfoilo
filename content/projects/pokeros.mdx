## 문제와 제약

토너먼트 운영에서는 좌석 배정, 테이블 이동, 딜러 로테이션, 포커 클락이 서로 연결됩니다. 한 화면에서 상태를 바꾸더라도 다른 운영자가 보는 화면에 같은 결과가 반영되어야 합니다.

기존 개발 기반이 없는 환경에서 프론트엔드, API, 데이터 저장, 실시간 통신과 배포 환경을 함께 구성했습니다. 단순히 화면을 만드는 것보다 **어떤 상태를 누가 확정하고, 연결이 끊겼을 때 무엇을 믿을 것인가**가 중요한 문제였습니다.

## 맡은 범위

React 운영 화면, Express API, Redis 기반 운영 상태, PostgreSQL 영속 데이터와 Docker 기반 실행·배포 구성을 다뤘습니다. 좌석·테이블·토너먼트·딜러 업무를 화면과 API의 경계로 옮기고 실시간 상태 전파를 연결했습니다.

## 핵심 판단

### 명령과 상태 전파를 분리했습니다

상태 변경은 HTTP API로 요청하고, 서버가 변경을 확정한 뒤 Socket.IO로 스냅샷을 전파하도록 구성했습니다. 클라이언트가 이벤트를 받아 임의로 상태를 추정하기보다 **서버가 확정한 결과를 표시**하도록 책임을 나눴습니다.

### 연결 성공과 동기화 완료를 구분했습니다

소켓이 다시 연결되었다고 해서 화면이 최신 상태인 것은 아닙니다. 재접속 후 권한 범위에 맞는 구독과 초기 스냅샷 조회를 수행하고, 재동기화에 실패하면 마지막 상태를 유지하되 변경 UI를 잠그는 구조를 적용했습니다.

### 업무 범위를 권한 범위와 맞췄습니다

매장·이벤트·토너먼트 범위를 API와 소켓 구독에 반영했습니다. 운영 데이터의 범위를 제한하는 일이 단순한 화면 필터에 머물지 않도록 서버 검증과 연결했습니다.

## 공통화와 개별 규칙

서버 검증, 확정 상태 전파, 재접속 복구는 공통 패턴으로 다뤘습니다. 반면 좌석 이동·테이블 배정·딜러 로테이션의 업무 규칙은 각각의 도메인에 남겼습니다. 같은 전송 수단을 쓴다는 이유만으로 서로 다른 운영 규칙까지 하나의 추상화로 묶지 않았습니다.

## 현장 적용을 위한 인터페이스

운영자가 다루는 좌석, 테이블, 일정 등의 개념을 화면의 기본 단위로 사용했습니다. 특히 동기화되지 않은 상태를 정상 상태처럼 보여주지 않고, 상태 표시와 재시도 경로를 제공하는 방식으로 현장 사용을 고려했습니다.

## 결과와 남은 검증

분리되어 있던 운영 업무를 웹/API와 실시간 상태 전파로 연결하는 기반을 구축했습니다. 기술 사례는 검토 시점의 프로젝트 자료를 기준으로 정리했으며, 모든 세부 기능이 같은 시점에 운영 배포되었다는 의미는 아닙니다.

처리량, 동시접속 규모, 수작업 대비 시간 절감률은 이 페이지의 성과 수치로 주장하지 않습니다. 이후에는 재동기화 성공률과 복구 시간처럼 사용자 경험에 직접 연결되는 지표를 별도로 측정할 수 있습니다.
